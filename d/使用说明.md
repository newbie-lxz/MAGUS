# D 阶段使用说明

## 1. 范围

D 只负责源码/API 误用验证。这里的 API 指 C/C++ 编程语言中的函数调用接口和调用序列，不是 Web 开发里的 HTTP API。

正式链路是：

```text
A：提取代码证据和 API/调用路径
B：挖掘可疑模式和候选样本
C：筛选并分流，P1/P2 以及已完成的 P0 输出到 c/out/*.jsonl
D：信任 c/out 队列，把其中的源码/API 假设转成 payload / PoC runner，执行验证并输出 confirmed 或 failed
```

D 不生成 HTTP 请求，不需要 `base_url`、端口、token，也不会输出 `*.http` payload。

## 2. C 需要给 D 什么

C 给 D 的正式动态验证队列目录是：

```text
c/out/
```

目录下可以有一个或多个 Stage C 假设文件：

```text
*.jsonl
```

D 的正式脚本会按文件名排序读取 `c/out/*.jsonl`，信任这些记录已经由 C 选为需要动态验证，并拒绝重复的 `project_id + hypothesis_id`。每个文件支持 JSONL，也支持一个 JSON 对象或 JSON 数组。

根目录完整链路 `make run-abcd` 使用流式模式：pipeline 会先启动 D 的 `stream_from_C.py` 监听当前 `C_OUTPUT` 文件，再启动 C。C 每 flush 一条完整的动态验证 JSONL 记录，D 就读取并验证；这些记录包括 `P1`/`P2`，以及已完成的 `P0`。C 结束后 pipeline 写入 done 标记，D 读完最后一批完整行后退出。流式模式只消费本次 `C_OUTPUT` 文件，独立 `make run-d` 仍按批处理方式读取所有 `c/out/*.jsonl`。

C 的审计输出不由 D 读取：

```text
c/audit/audit.jsonl  # P3，非漏洞/硬矛盾/证据缺失/处理错误/Stage C 超时
```

Stage C 的时间预算只控制是否继续提交候选，以及未完成 worker 是否转成
`P3` 超时审计记录。已完成的 `P0` 会写入 `c/out/*.jsonl` 交给 D 做
route-bound 动态验证。D 只对 `P0` 施加每条 10 秒执行 timeout；
`P1`/`P2` 不受 D timeout 限制。

## 3. 推荐输入格式

源码/API 误用类推荐格式：

```json
{
  "project_id": "openssl",
  "sample_id": "path_000001",
  "hypothesis_id": "hyp_9001",
  "claim": "可能存在未检查返回值导致空指针解引用",
  "CWE_candidates": ["CWE-476"],
  "priority": "P1",
  "agent_verdict": "candidate_for_d",
  "routing_decision": "candidate_for_d",
  "suspicion_reason": "red_team_stable_needs_dynamic_verification",
  "route": "parse_cert",
  "attack_path": ["parse_cert -> ASN1_OCTET_STRING_new -> dereference"],
  "file": "crypto/asn1/a_object.c",
  "line": 88,
  "evidence_slice": "obj = ASN1_OCTET_STRING_new(); return obj->length;",
  "preconditions": ["requires malformed DER input"],
  "verification_context": {
    "repo_path": "/datasets/openssl",
    "config_cmd": "./Configure enable-asan",
    "build_cmd": "make -j4",
    "run_cmd": "${PYTHON} poc_parse_cert.py",
    "oracle": {
      "failure_patterns": [
        "AddressSanitizer",
        "Segmentation fault",
        "null pointer"
      ],
      "expect_nonzero_exit": true
    },
    "input_source": "DER certificate file",
    "seed_inputs": ["empty DER", "oversized DER", "malformed bytes"]
  }
}
```

Stage C 当前写 `CWE_candidates`，D 也能读取 `cwe_candidates`。新输出优先沿用 Stage C 的实际字段名。

D 生成 targets 的硬性字段：

```text
project_id
hypothesis_id
route
```

D verifier 的硬性证据字段：

```text
project_id
sample_id
hypothesis_id
route
file
line
evidence_slice
```

推荐同时提供但不作为硬性 evidence gate 的字段：

```text
claim
CWE_candidates 或 cwe_candidates
preconditions
attack_path
confidence
priority
agent_verdict
routing_decision
suspicion_reason
verification_context
```

D 不再根据 `agent_verdict` 或 `priority` 做准入判断。C 负责保证只有需要 D 动态验证的记录进入 `c/out/*.jsonl`；D 会验证 `c/out` 里的全部记录。

自动执行验证还需要：

```text
verification_context.repo_path
verification_context.run_cmd 或 poc_cmd 或 test_cmd
verification_context.oracle
```

`verification_context.oracle` 可以只使用传统的 `failure_patterns` 和
`expect_nonzero_exit`，也可以加上 route-bound 约束：

```text
required_patterns        # 确认前必须同时出现在运行输出中的模式
failure_code_patterns    # 把运行输出中的特定模式映射为失败码
```

如果运行能触发项目中某个漏洞但不能证明是当前 `route` / source API 序列触发，
D 不会写 confirmed，而是输出 `NOT_ROUTE_BOUND` 失败回流。

如果 C 不想改核心输出逻辑，也可以把这些字段放到 D 的 sidecar：

```text
d/memberD_verifier/02_run_with_C/verification_contexts.jsonl
```

sidecar 支持按 `project_id`、`route`、`hypothesis_id` 绑定，优先级是：

```text
hypothesis_id > route > project_id
```

示例：

```json
{"project_id":"juliet_small_c","repo_path":"srcs/juliet-small","test_cmd":"./repros/run_juliet_case.sh ${file} ${entry_symbol}","oracle":{"failure_patterns":["AddressSanitizer","Segmentation fault"],"expect_nonzero_exit":false}}
```

自动脚本会先生成 `targets.auto.json`，如果 sidecar 存在，再生成 `targets.executable.json` 并交给原 verifier 执行。

`route` 表示入口函数、`source_path::function` 或调用路径，不表示 HTTP 路由。

## 4. 正式运行

进入：

```text
d/memberD_verifier/02_run_with_C
```

运行：

```text
./01_auto_attack_from_C_linux.sh
```

流程会生成 `targets.auto.json`，再运行 verifier。

也可以从仓库根目录运行：

```text
make run-d
```

完整 root 链路是：

```text
make run-abcd
```

这条命令会在 Stage C 运行期间同步运行 Stage D。D 只读 C 当前输出文件，不写回 `c/out`，并且只处理以换行结束的完整 JSONL 记录。D 的批处理和流式模式共用 `02_run_with_C/.stage_d_output.lock`，因此不能同时运行两个写同一 `output` 目录的 D 进程。

D 当前只使用 Python 标准库；`01_setup_linux.sh` 在没有真实 requirements 依赖时会创建不带 pip 的 `.venv`。

## 5. 输出文件

输出目录：

```text
d/memberD_verifier/02_run_with_C/output
```

关键文件：

```text
verification.jsonl
verification.failed.jsonl
verification.summary.md
payloads/*.payload.py
payloads/*.api-plan.json
```

`verification.jsonl` 是 confirmed 结果。  
`verification.failed.jsonl` 是信息不足、环境缺失或 oracle 未命中的失败回流。  
`payloads/*.api-plan.json` 是源码/API 验证计划。  
`payloads/*.payload.py` 是 verifier 自动调用的可执行 runner。

## 6. 常见失败

`repo_path does not exist`  
源码仓库路径不存在。

`run_cmd/poc_cmd/test_cmd is missing`  
C 没给能触达可疑 API 序列的运行命令。

`setup/build command failed`  
配置或编译失败，需要检查 `config_cmd` / `build_cmd`。

`payload did not satisfy oracle`  
payload 跑了，但没有命中 oracle。可能是假设不成立，也可能是 harness 或 oracle 不准。

`NOT_ROUTE_BOUND`  
payload 或测试命令运行了，但 oracle 不能证明当前候选 `route` 被执行并产生证据。
这种情况需要补 route marker、指定更精确的 harness，或调整 sidecar 里的
`required_patterns` / `failure_code_patterns`。

`missing required fields`  
C 放入 `c/out` 的记录缺少 D 必需字段，需要回到 C 修正分流输出。
