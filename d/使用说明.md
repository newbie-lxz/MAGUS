# D 阶段使用说明

## 1. 范围

D 只负责源码/API 误用验证。这里的 API 指 C/C++ 编程语言中的函数调用接口和调用序列，不是 Web 开发里的 HTTP API。

正式链路是：

```text
A：提取代码证据和 API/调用路径
B：挖掘可疑模式和候选样本
C：筛选并分流，P1/P2 以及已完成的 P0 输出到 c/out/*.jsonl
D：信任 c/out 队列，把其中的源码/API 假设转成 payload / PoC runner，执行验证并输出 reportable/failed。reportable 包括 D confirmed，以及 D 明确缺少 oracle 能力时保留的 Stage C 判断。
Report：读取 D 的 reportable/failed 输出并生成最终漏洞报告
```

D 不生成 HTTP 请求，不需要 `base_url`、端口、token，也不会输出 `*.http` payload。

## 2. C 需要给 D 什么

C 给 D 的正式动态验证队列目录是：

```text
c/out/
```

目录下可以有一个或多个 Stage C 假设文件：

```text
*.jsonl
```

D 的正式脚本会按文件名排序读取 `c/out/*.jsonl`，信任这些记录已经由 C 选为需要动态验证，并拒绝重复的 `project_id + hypothesis_id`。每个文件支持 JSONL，也支持一个 JSON 对象或 JSON 数组。

根目录完整链路 `make run-abcd` 使用流式模式：pipeline 会先启动 D 的 `stream_from_C.py` 监听当前 `C_OUTPUT` 文件，再启动 C。C 每 flush 一条完整的动态验证 JSONL 记录，D 就读取并验证；这些记录包括 `P1`/`P2`，以及已完成的 `P0`。C 结束后 pipeline 写入 done 标记，D 读完最后一批完整行后退出，然后 Report 从 D 输出生成最终报告。流式模式只消费本次 `C_OUTPUT` 文件，并把 D 输出写到 `output/<run-name>/`；`<run-name>` 来自 `REPORT_RUN_NAME` / `--report-run-name`，未提供时使用 Stage A 输入的 `project_id`。独立 `make run-d` 仍按批处理方式读取所有 `c/out/*.jsonl`，写入固定 `output/`，并在 D 校验通过后运行 Report。两种模式只有在显式传入 `--contexts` / `--d-contexts` 或 `D_CONTEXTS` 时才加载项目执行 sidecar。

Stage C 固定执行三轮双 agent 审计：红队 `red_proposer`、蓝队 `blue_challenger`、红队 `red_rebuttal`，完成记录写入 `agent_rounds`。`P1` 表示最终红队回应仍认为有漏洞且至少两轮支持漏洞，包括第一轮误判无漏洞后由蓝队和红队纠正为漏洞，或第一轮有漏洞、蓝队挑战、第三轮仍确认漏洞。`P2` 表示至少一轮报过漏洞但最终支持不稳定，例如第一轮报漏洞而后续两轮都否定。LLM/API 失败不算无漏洞票，会以 `stage_c_llm_error` 或 `stage_c_partial_llm_error` 保留在审计/候选原因里。

C 的审计输出不由 D 读取：

```text
c/audit/audit.jsonl  # P3，非漏洞/硬矛盾/证据缺失/处理错误/Stage C 超时
```

Stage C 的时间预算只控制是否继续提交候选，以及未完成 worker 是否转成
`P3` 超时审计记录。已完成的 `P0` 会写入 `c/out/*.jsonl` 交给 D 做
route-bound 动态验证。D 只对 `P0` 施加每条 10 秒执行 timeout；
`P1`/`P2` 不受 D timeout 限制。

## 3. 推荐输入格式

源码/API 误用类推荐格式：

```json
{
  "project_id": "openssl",
  "sample_id": "path_000001",
  "hypothesis_id": "hyp_9001",
  "claim": "可能存在未检查返回值导致空指针解引用",
  "CWE_candidates": ["CWE-476"],
  "priority": "P1",
  "agent_verdict": "candidate_for_d",
  "routing_decision": "candidate_for_d",
  "suspicion_reason": "multi_agent_stable_needs_dynamic_verification",
  "route": "parse_cert",
  "attack_path": ["parse_cert -> ASN1_OCTET_STRING_new -> dereference"],
  "file": "crypto/asn1/a_object.c",
  "line": 88,
  "evidence_slice": "obj = ASN1_OCTET_STRING_new(); return obj->length;",
  "preconditions": ["requires malformed DER input"]
}
```

Stage C 当前写 `CWE_candidates`，D 也能读取 `cwe_candidates`。CWE 只作为 D oracle profile 选择的辅助信号；没有 CWE 时，D 会从 API 名、`route`、`attack_path`、`evidence_slice` 和 `claim` 中选择 profile。新输出优先沿用 Stage C 的实际字段名。Stage C 只负责输出漏洞假设、代码位置和路由证据；verifier、执行上下文和 oracle 由 Stage D 生成或通过 D 侧 sidecar 提供。

D 生成 targets 的硬性字段：

```text
project_id
hypothesis_id
route
```

D verifier 的硬性证据字段：

```text
project_id
sample_id
hypothesis_id
route
file
line
evidence_slice
```

推荐同时提供但不作为硬性 evidence gate 的字段：

```text
claim
CWE_candidates 或 cwe_candidates
preconditions
attack_path
confidence
priority
agent_verdict
routing_decision
suspicion_reason
```

D 不再根据 `agent_verdict` 或 `priority` 做准入判断。C 负责保证只有需要 D 动态验证的记录进入 `c/out/*.jsonl`；D 会验证 `c/out` 里的全部记录。

自动执行验证需要由 D 侧 sidecar 或显式 targets 提供执行上下文；核心 target generator 不自动附加 benchmark 或项目专用执行配置。需要提供：

```text
repo_path
run_cmd 或 poc_cmd 或 test_cmd
oracle
```

D 的 target generator 先生成项目无关的 source/API target 和 oracle profile。真正的仓库路径、构建命令、运行命令、route marker、失败 marker、unsupported marker 来自显式 sidecar 或显式 target。`oracle_profiles.py` 只保留通用 profile 选择、可审计的 API-family 语义模型和 `MAGUS_ORACLE_*` 语义模式，不能包含 Juliet 或其他 benchmark 专用代码。自动生成的 source/API payload runner 会把 `MAGUS_D_PROJECT_ID`、`MAGUS_D_SAMPLE_ID`、`MAGUS_D_HYPOTHESIS_ID`、`MAGUS_D_ROUTE`、`MAGUS_D_FILE`、`MAGUS_D_LINE`、`MAGUS_D_ENTRY_SYMBOL`、`MAGUS_D_ORACLE_PROFILE_ID`、`MAGUS_D_PAYLOAD`、`MAGUS_D_PAYLOAD_MARKER` 和 `MAGUS_D_CONFIRM_PATTERNS_JSON` 注入到运行命令环境中；任意项目 harness 都可以读取这些变量，输出 `MAGUS_ROUTE_EXECUTED` 和对应的 `MAGUS_ORACLE_*` marker。搜索路径类 profile 是通用 profile，覆盖 `putenv`、`_putenv`、`_wputenv`、`SetEnvironmentVariableA/W`、`SearchPathA/W`、`SetDllDirectoryA/W` 和 `AddDllDirectory`。资源生命周期 profile 按 API 家族和运行环境分开：用户态 fd 覆盖 `open`/`socket`/`pipe` 等到 `close`，C stdio 覆盖 `fopen`/`fdopen`/`popen` 到 `fclose`/`pclose`，Win32 HANDLE 覆盖 `CreateFile*`/HANDLE API 到 `CloseHandle`，Linux kernel 覆盖 `filp_open`/`fput`、`kmalloc`/`kfree`、`kobject_get`/`kobject_put` 等内核语义。kernel profile 必须由 KUnit、kselftest、QEMU、syzkaller repro 或模块 harness 等显式执行上下文承载，不能复用用户态 `open`/`close` oracle。benchmark 或运行环境 helper 只能放在 `tools/` 或测试脚本里，并通过命令行 sidecar 显式接入。

对返回值检查类 oracle，单纯强制 API 失败不等于 confirmed；profile 还必须命中失败后的 route-bound 语义证据，
例如失败后的 `RevertToSelf` 成功路径行为，或 `RpcImpersonateClient` 失败后 route 正常完成且错误未传播。

sidecar `oracle` 可以只使用传统的 `failure_patterns` 和
`expect_nonzero_exit`，也可以加上 route-bound 约束：

```text
required_patterns        # 确认前必须同时出现在运行输出中的模式；自动 target 默认要求 MAGUS_ROUTE_EXECUTED
capability_patterns      # 证明 harness 确实运行了该 profile 的语义 oracle；资源生命周期 profile 默认要求 MAGUS_ORACLE_RAN profile=<id>
failure_code_patterns    # 把运行输出中的特定模式映射为失败码
unsupported_patterns     # route 已执行但 D oracle 不支持当前漏洞语义时返回 UNSUPPORTED_ORACLE
```

如果运行能触发项目中某个漏洞但不能证明是当前 `route` / source API 序列触发，
D 不会写 confirmed，而是输出 `NOT_ROUTE_BOUND` 失败回流。
如果当前 `route` 已执行，但 D 没有可用 oracle profile、资源生命周期 harness 缺少 capability marker，或明确返回 `UNSUPPORTED_ORACLE`，D 不会把它伪装成
`NOT_EXPLOITABLE`。只有 Stage C `P0`/`P1` 会在 `verification.jsonl` 写 `stage_c_preserved`，保留 Stage C 的
`priority` / `routing_decision` / `suspicion_reason` / `agent_verdict`；`P2` 会进入
`verification.failed.jsonl`，`failure_code=UNSUPPORTED_ORACLE`。

这些字段放在 D 的 sidecar，并通过 `pipeline.py d --contexts`、`pipeline.py abcd --d-contexts`、`make run-d D_CONTEXTS=...` 或 `make run-abcd D_CONTEXTS=...` 显式传入：

```text
d/memberD_verifier/02_run_with_C/verification_contexts.<run>.jsonl
```

sidecar 支持按 `project_id`、`route`、`hypothesis_id` 绑定，优先级是：

```text
hypothesis_id > route > project_id
```

示例：

```json
{"project_id":"custom_source_api","repo_path":"/datasets/custom-source-api","test_cmd":"./repros/run_case.sh ${file} ${entry_symbol}","oracle":{"failure_patterns":["AddressSanitizer","Segmentation fault"],"expect_nonzero_exit":false}}
```

自动脚本会先生成 `targets.auto.json`。如果显式传入 sidecar，再生成 `targets.executable.json` 并交给原 verifier 执行；如果没有任何可执行上下文，D 仍会生成 payload/plan，但结果会以 `ENV_MISSING` 进入失败回流。

`route` 表示入口函数、`source_path::function` 或调用路径，不表示 HTTP 路由。

## 4. 正式运行

进入：

```text
d/memberD_verifier/02_run_with_C
```

运行：

```text
./01_auto_attack_from_C_linux.sh
```

流程会生成 `targets.auto.json`，再运行 verifier。需要 sidecar 时把路径作为第一个参数传入：

```text
./01_auto_attack_from_C_linux.sh verification_contexts.<run>.jsonl
```

也可以从仓库根目录运行：

```text
make run-d
```

带 sidecar：

```text
make run-d D_CONTEXTS=d/memberD_verifier/02_run_with_C/verification_contexts.<run>.jsonl
```

完整 root 链路是：

```text
make run-abcd
```

这条命令会在 Stage C 运行期间同步运行 Stage D。D 只读 C 当前输出文件，不写回 `c/out`，并且只处理以换行结束的完整 JSONL 记录。D 的批处理和流式模式共用 `02_run_with_C/.stage_d_output.lock`，因此不能同时运行两个 D 写进程。

带 sidecar：

```text
make run-abcd D_CONTEXTS=d/memberD_verifier/02_run_with_C/verification_contexts.<run>.jsonl
```

D 当前只使用 Python 标准库；`01_setup_linux.sh` 在没有真实 requirements 依赖时会创建不带 pip 的 `.venv`。

## 5. 输出文件

批处理输出目录：

```text
d/memberD_verifier/02_run_with_C/output
```

流式 root 链路输出目录：

```text
d/memberD_verifier/02_run_with_C/output/<run-name>
```

关键文件：

```text
verification.jsonl
verification.failed.jsonl
verification.summary.md
payloads/*.payload.py
payloads/*.api-plan.json
```

`verification.jsonl` 是 reportable 结果：`confirmed` 表示 D route-bound 动态确认且命中当前 `oracle_profile_id` 的语义证据，`stage_c_preserved` 表示 D 到达 route 但缺少 oracle 能力，因此保留 Stage C `P0`/`P1` 判断。
`verification.failed.jsonl` 是信息不足、环境缺失、route 不可归因、支持的 oracle profile 明确未命中，或 `P2 + UNSUPPORTED_ORACLE` 的失败回流。`NOT_EXPLOITABLE` 只用于支持的 oracle profile 已运行但未确认漏洞；D 能力缺口必须用 `UNSUPPORTED_ORACLE`，不能伪装成不可利用。生成的 plan 和 D 记录可能包含 `oracle_profile_id` / `oracle_profile_supported`，用于审计 profile 覆盖情况。
`payloads/*.api-plan.json` 是源码/API 验证计划。  
`payloads/*.payload.py` 是 verifier 自动调用的可执行 runner。

最终漏洞报告由 `pipeline.py report` 调用 `report/code/generate_report.py` 读取上面的 D 输出后生成。报告目录固定为 `report/<run-name>/`，`<run-name>` 默认取 D 输出中唯一的 `project_id`。需要手工指定目录名时设置 `REPORT_RUN_NAME=<name>` 或 `pipeline.py report --run-name <name>`。

```text
report/<run-name>/verification.report.jsonl
report/<run-name>/verification.report.md
```

报告从 D `verification.jsonl` 的 reportable 记录生成；每条报告包含漏洞位置（文件路径、行号、route）、漏洞类型、风险等级、触发条件、运行证据和 payload/plan 引用。`report/code/validate_report.py` 会校验报告行数与 `verification.jsonl` reportable 行数一致，并接受 `confirmed` / `P0` 或 `P1` 的 `stage_c_preserved` 状态。

## 6. 常见失败

`repo_path does not exist`  
源码仓库路径不存在。

`run_cmd/poc_cmd/test_cmd is missing`  
C 没给能触达可疑 API 序列的运行命令。

`setup/build command failed`  
配置或编译失败，需要检查 `config_cmd` / `build_cmd`。

`payload did not satisfy oracle`  
payload 跑了，但没有命中 oracle。可能是假设不成立，也可能是 harness 或 oracle 不准。

`NOT_ROUTE_BOUND`  
payload 或测试命令运行了，但 oracle 不能证明当前候选 `route` 被执行并产生证据。
这种情况需要补 route marker、指定更精确的 harness，或调整 sidecar 里的
`required_patterns` / `failure_code_patterns`。

`missing required fields`  
C 放入 `c/out` 的记录缺少 D 必需字段，需要回到 C 修正分流输出。
